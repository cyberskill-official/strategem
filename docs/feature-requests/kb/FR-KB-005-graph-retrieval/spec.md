## §1 - Description (BCP-14 normative)

This FR exposes the knowledge graph (FR-KB-001) as a hybrid-retrieval query API: given a la so's components, it traverses the graph and returns the related entities, the relations that connect them, and the citations attached along the way. It is the graph arm that FR-RAG-002 was built to accept - the second retrieval source that FR-RAG-002 fuses with its vector arm (Claude-06 s3.3). It does NOT own the graph shape or store (FR-KB-001) nor the classical text (FR-KB-003); it is a read-only query layer over both.

The API SHALL accept a `GraphQuery` carrying the `system`, a set of seed tokens (the salient chart entities: can, chi, cung, sao, mon, than, and the detected cách cục ids), and traversal bounds. It SHALL resolve each seed token to a graph node id, traverse the graph over the Tam Thuc relations - ngũ hành sinh/khắc (生/剋); địa chi hình/xung/phá/hại/hợp (刑/沖/破/害/合); vị trí ký cung/lạc cung/lâm (寄宮/落宮/臨); trạng thái thừa and vượng-tướng-hưu-tù-tử (乘/旺-相-休-囚-死) (Claude-06 s3.2) - to a bounded hop depth, and SHALL return ranked `GraphHit` records. Each hit SHALL carry the related node, the relation path that reached it from a seed, and the citation ids collected along that path, filtered to `system in {system, all}`.

A seed token that resolves to no node SHALL be surfaced in `seeds_unresolved`, never silently dropped. Citations SHALL be collected from the cách cục / thần sát nodes on the path (which carry the FR-KB-002 pattern citations) and from any citation on a traversed edge, de-duplicated, and each SHALL resolve into the FR-KB-003 corpus. A traversed relation that carries no citation SHALL still be returned as structural context, but with an empty `citations` list, so the consumer (FR-RAG-003, via FR-RAG-002) can only turn a graph result into a cited claim when a citation actually exists. The query SHALL be deterministic given the graph state and the query, and SHALL be read-only over the graph and the corpus.

## §2 - Why this design (rationale for humans)

Vector retrieval finds passages semantically near a query, but Tam Thuc interpretation runs on relational structure the vectors do not see: this door on this palace is generated by that stem, which clashes with that branch, and the star sitting here is vượng in this season (Claude-06 s3.3). Those facts live in the graph as edges, and the only way to pull the exact rules that bear on this particular chart is to start from the chart's own entities and traverse. That is why FR-RAG-002 has two arms and why the graph arm is not optional to the design even though it is optional to the P0 runtime: without it, an interpretation is grounded in what the classics say near the words of the question, but not in which relations connect the parts of this chart. This FR is the traversal that supplies the second kind of grounding.

Returning the citations along the path, not just the related nodes, is what keeps the graph arm inside the anti-hallucination contract. A relation on its own ("Mộc sinh Hỏa") is structural context; it becomes a citable claim only when a cách cục node on the path carries a FR-KB-002 pattern citation that resolves into the FR-KB-003 corpus. By collecting exactly those citations and returning an empty list where none exist, this FR hands FR-RAG-002 a result that FR-RAG-003's guard can treat correctly: relations with citations can ground a claim, relations without them are context that cannot. Surfacing unresolved seeds rather than dropping them matters for the same honesty reason - a chart entity the graph does not know about is a coverage gap to see, not a silent omission that makes the graph arm look more complete than it is.

## §3 - Contract (query, traversal, citations)

### Query and result (`tamthuc_kb/graph/query.py`)

```python
class GraphQuery(BaseModel):
    model_config = ConfigDict(extra="forbid")
    system: System
    seeds: list[str]                 # entity tokens or node ids: can/chi/cung/sao/mon/than + cach_cuc ids
    max_hops: int = 2                # bounded traversal depth
    rels: list[EdgeRel] | None = None    # restrict to certain relations; None = all Tam Thuc relations
    k: int = 12

class GraphRelation(BaseModel):
    src: str; rel: EdgeRel; dst: str
    src_label: str; dst_label: str
    attrs: dict = {}                 # e.g. {"state": "vuong"} for a trang_thai edge
    citations: list[str] = []        # citation_ids on this edge, if any

class GraphHit(BaseModel):
    node_id: str                     # the related entity reached
    label: str
    label_han: str | None
    kind: NodeKind
    system: System
    path: list[GraphRelation]        # the relations traversed from a seed to this node
    citations: list[str]             # de-duped union of citations along the path + on the node
    score: float                     # closeness rank (fewer hops + more seed support -> higher)

class GraphQueryResult(BaseModel):
    hits: list[GraphHit]             # length <= k, ranked
    seeds_resolved: list[str]        # seed tokens that resolved to node ids
    seeds_unresolved: list[str]      # tokens with no node (surfaced, not dropped)
    filter: dict                     # the applied system filter, for audit
```

class GraphQueryService:

    def query(self, q: GraphQuery) -> GraphQueryResult:
        # 1. resolve seeds -> node ids (surface unresolved)

`citations.py` also offers `resolvable(citation_ids)` which checks each collected id against `ClassicalStore.resolve_citation`, so a citation the graph carries but the corpus cannot resolve is caught (a dangling citation shared with the FR-KB-003 check).

### The FR-RAG-002 seam

FR-RAG-002 defines a `GraphRetriever` protocol (`available()`, `traverse(ctx, k)`) with a `NullGraphRetriever` default until this FR lands. This FR is the server this protocol's real client calls: `traverse` maps FR-RAG-002's `ChartContext` (`system`, `entities`, `cach_cuc_ids`) onto a `GraphQuery` and maps `GraphHit`s back to FR-RAG-002's `GraphHit`s. When this FR is present, `available()` returns true and FR-RAG-002's graph arm activates with no change above it.

## §4 - Acceptance criteria

1. A `GraphQuery` with seeds `["丙", "cung_1", "Sinh_mon"]` and `system=qimen` resolves the known tokens to node ids and returns ranked `GraphHit`s; an unknown token appears in `seeds_unresolved`, not silently dropped.
2. Traversal honors `max_hops` and `rels`: with `rels=[sinh]` only sinh edges are followed; a two-hop query reaches a node two relations away and records the full `path`.
3. The per-system filter is enforced: a `qimen` query never returns a `liuren`/`taiyi`-only node; `system=all` primitives (can, chi, ngũ hành) are included.
4. Citations are collected along the path and de-duped; a hit through a cách cục node carries that node's FR-KB-002 citations, and every returned `citation_id` resolves via FR-KB-003 (`resolve_citation`), with dangling ids reported.
5. A traversed relation with no citation returns as a `GraphHit`/`GraphRelation` with an empty `citations` list (structural context), never fabricated citations.
6. The query is deterministic: identical graph state and query yield an identical ranked result across runs (stable tie-break on score, hop distance, node id); the FR-RAG-002 `GraphRetriever` client maps context and hits without loss on the fixture.

## §9 - Open questions

- Whether primitive relations (Mộc sinh Hỏa) should carry their own citations or stay structural-only. Default: structural-only at MVP; the cited grounding rides on the cách cục / thần sát nodes (FR-KB-002); add edge citations only where a specific classical line documents a specific relation. Revisit from FR-RAG-006 retrieval quality.
- Hop bound. Default: `max_hops=2` (one- and two-hop neighborhoods, the shapes FR-KB-001 kept relational and cheap in SQL); deeper traversal is a reason to reconsider a graph DB, not to raise the default blindly.
- Scoring of graph hits before fusion. Default: hop distance ascending plus seed-support count, deterministic tie-break; FR-RAG-002 applies reciprocal-rank fusion across arms, so this FR only needs a stable within-arm rank. Tune with FR-RAG-006 evidence.

## §10 - Failure modes inventory

| Mode | Trigger | Required behavior |
|---|---|---|
| Silent seed drop | an unknown chart token is ignored | surfaced in `seeds_unresolved`; never guessed into a node |
| Fabricated citation | a structural relation reported as cited | empty `citations` where none exist; only real, resolvable ids are attached |
| Dangling citation | a graph citation the corpus cannot resolve | `resolvable()` reports it (shared with the FR-KB-003 check); not returned as valid grounding |
| Cross-system leak | traversal returns foreign-system nodes | `system in {system, all}` filter on every hop; isolation test |
| Unbounded traversal | traversal without a hop cap | `max_hops` enforced; the query is bounded and cheap |
| Non-deterministic rank | unstable sort of hits | stable tie-break on (score desc, hops asc, node_id); determinism test |
| Hard-required by RAG-002 in P0 | code assumes this FR exists early | `GraphRetriever.available()` gate; FR-RAG-002 degrades to vector-only until this lands |

## §11 - Notes

This FR is the second half of the hybrid retrieval the architecture calls for, and its whole value is relational grounding that vector search cannot give. Two things keep it honest: it returns citations only where they truly exist (empty lists for structural-only relations, so FR-RAG-003's guard never sees a fabricated ground), and it surfaces unresolved seeds so the graph arm's coverage is visible. Keep it read-only over both the graph and the corpus - it queries FR-KB-001 and FR-KB-003, it never writes them. Because FR-RAG-002 already ships the `GraphRetriever` protocol and the degraded path, landing this FR is a clean activation, not a rewire above it. The package `tamthuc_kb` is shared with FR-KB-001/002/003/004; this FR adds `graph/query.py`, `resolve.py`, and `citations.py` to the existing `graph/` module, so the knowledge base stays one installable, mypy-clean unit.
