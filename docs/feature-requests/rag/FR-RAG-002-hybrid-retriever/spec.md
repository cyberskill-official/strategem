## §1 - Description (BCP-14 normative)

This FR is the retrieval half of the RAG branch: given a user query, a chart context, and a system, it returns the ranked classical passages an interpretation will be grounded in. Retrieval SHALL be hybrid - a vector semantic arm over the FR-RAG-001 index plus a knowledge-graph arm over FR-KB-005 - fused into one ranked list of chunks with their citations (Claude-06 s4.2). This mirrors the two-source design: retrieve văn bản cổ by meaning, and traverse the knowledge graph for the relations among the chart's components (Claude-06 s3.3).

The retriever SHALL accept a `RetrievalRequest` (query text, `system`, and a chart context: the detected `cach_cuc` ids and the salient chart entities - can, chi, cung, sao, mon, than) and SHALL return top-k `RetrievedChunk` records, each carrying the three text layers, a `citation_id`, a fused score, and which arm(s) contributed it. A per-system metadata filter SHALL be applied to both arms: a QiMen query SHALL retrieve only `qimen` and `all` material, never `liuren`/`taiyi`-only material.

The graph arm depends on FR-KB-005, which is phase P2 while this FR is P0 (see section 9). The retriever SHALL therefore treat the graph arm as optional at runtime: when FR-KB-005 is unavailable it SHALL degrade to vector-only retrieval and set a flag on the result, and it SHALL NOT fail. Fusion SHALL be deterministic given the two input lists (reciprocal-rank fusion by default), and de-duplication SHALL be by `citation_id`/`unit_id` so the same passage reached by both arms appears once with a combined score.

## §2 - Why this design (rationale for humans)

Vector search alone finds passages that are semantically near the query, but it misses the relational structure that Tam Thuc interpretation runs on: this door on this palace is generated by that stem, which clashes with that branch. Those relations live in the knowledge graph (Claude-06 s3.3), and traversing it from the chart's own entities pulls in the exact rules that bear on this chart, cited. Fusing the two arms gives an interpretation both kinds of grounding - textual (what the classics say near this query) and relational (which rules connect this chart's parts) - which is the hybrid retrieval both source sets call for.

Making the graph arm optional is a phase-sequencing decision forced by the dependency graph and worth being explicit about. FR-RAG-002 is P0 (the end-to-end QiMen demo needs retrieval), but the knowledge-graph query API (FR-KB-005) is scheduled P2. Rather than block the P0 demo on a P2 module, this FR ships the vector arm as the hard P0 requirement and wires the graph arm behind a capability check that activates when FR-KB-005 exists. Until then the product retrieves by semantics only, clearly flagged; when the graph lands, relational grounding switches on with no change to FR-RAG-003 above it. This keeps the critical path moving while honoring the eventual hybrid design.

## §3 - Contract (request, arms, fusion)

### Request and result (`tamthuc_rag/retrieve.py`)

```python
class ChartContext(BaseModel):
    system: System
    cach_cuc_ids: list[str] = []      # detected patterns (from the la so envelope)
    entities: list[str] = []          # salient can/chi/cung/sao/mon/than tokens for graph seeding

class RetrievalRequest(BaseModel):
    query: str
    context: ChartContext
    k: int = 8

class RetrievedChunk(BaseModel):
    citation_id: str
    unit_id: str
    system: System
    source: str
    han: str | None
    bach_thoai: str | None
    dich: str | None
    score: float                       # fused score
    arms: list[str]                    # subset of {"vector", "graph"}

class RetrievalResult(BaseModel):
    chunks: list[RetrievedChunk]       # length <= k, ranked
    graph_arm_used: bool               # False when FR-KB-005 unavailable (degraded)
    filter: dict                       # the applied metadata filter, for audit
```

### Vector arm

Embed `query` with the same `Embedder` FR-RAG-001 indexed with (dimension/model must match the index), then `VectorStore.query(vector, k=k*over_fetch, flt={system in [system, all]})`. Because chunks are per-layer (FR-RAG-001), collapse hits to their `unit_id`, keeping the best-scoring layer and joining the aligned layers for display.

### Graph arm (`tamthuc_rag/graph.py`)

A thin client over FR-KB-005's hybrid-retrieval query API. ## §4 - Acceptance criteria

1. A retrieval request returns up to `k` ranked `RetrievedChunk` records, each with its `citation_id`, the available text layers, a fused score, and the contributing arms.
2. The per-system filter is enforced on both arms: a `qimen` request never returns a `liuren`/`taiyi`-only chunk; `all` material is included.
3. With the graph arm available (stub `GraphRetriever`), a passage returned by both arms appears once with `arms=["vector","graph"]` and a combined score outranking a single-arm passage of equal base rank.
4. With the graph arm unavailable (`NullGraphRetriever`), retrieval succeeds vector-only, `graph_arm_used=False`, and no error is raised - the P0 degraded path.
5. Fusion is deterministic: identical arm inputs yield an identical ranked list across runs.
6. Vector-arm layer collapse returns one entry per `unit_id` with aligned layers joined, not three separate rows for the same unit.

## §9 - Open questions

- Phase inversion (flagged for the human sequencer): FR-RAG-002 is P0 but its `depends_on` lists FR-KB-005, which is P2. Resolution encoded here: the vector arm is the hard P0 requirement; the graph arm is optional at runtime and off until FR-KB-005 ships, at which point it activates with no change above it. The backlog SHOULD schedule the vector-only slice in P0 and the graph-arm activation with FR-KB-005 in P2, or pull FR-KB-005 forward. Left for the operator to decide; the code degrades either way.
- RRF vs a learned/weighted fusion. Default: RRF (parameter-light, robust, deterministic); revisit with FR-RAG-006 eval evidence once both arms are live.
- Over-fetch factor for the vector arm before layer collapse and fusion. Default: fetch `k * 4`, collapse, then fuse to `k`; tune from eval.

## §10 - Failure modes inventory

| Mode | Trigger | Required behavior |
|---|---|---|
| Graph arm hard-required | code assumes FR-KB-005 exists in P0 | `GraphRetriever.available()` gate; `NullGraphRetriever` default; retrieval degrades to vector-only, never fails |
| Cross-system leak | either arm returns foreign-system material | metadata filter `system in {system, all}` on both arms; isolation test |
| Embedder/index mismatch | query embedder differs from index model/dim | inherit FR-RAG-001's reindex-required guard; do not query with a mismatched space |
| Duplicate passage | same unit from both arms as two rows | de-dup by `citation_id`/`unit_id`; merged entry carries both arms |
| Non-deterministic ranking | unstable sort or dict-order fusion | RRF + stable tie-break (score, ordinal, citation_id); determinism test |
| Empty retrieval | no passage passes the filter | return empty `chunks`; FR-RAG-003 must treat empty grounding as no-claim, not free-memory generation |

## §11 - Notes

Hybrid retrieval is the mechanism that keeps interpretation grounded in both the classics and the chart's own relational structure. The one thing to get right beyond the fusion is the degraded path: because FR-KB-005 sits in a later phase, the P0 product must retrieve well on the vector arm alone, and the graph arm must be a clean, flagged enhancement rather than a hard dependency that stalls the critical path. An empty retrieval result is not a failure of this FR - it is a signal to FR-RAG-003 to decline a claim, which is the anti-hallucination contract working as designed.
